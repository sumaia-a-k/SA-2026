A* Search

Intelligent Search Algorithms · Latakia University · Lesson 3 of 3: Heuristics → Greedy → A*

The idea

UCS uses only the cost so far (g). Greedy uses only the guess (h). A* uses both.

f(n) = g(n) + h(n)
g(n)the real cost from the start to n (we already paid it)
h(n)a guess of the cost from n to the goal
f(n)a guess of the cost of the whole trip from S to G that goes through n
A* in one sentence: always expand the node with the smallest f = g + h: the node that is on the cheapest-looking whole trip.

Real life: "I already drove 10 km (g). The GPS says about 8 km are left (h). So this trip is about 18 km (f)."

Not sure about admissible and consistent? Read lesson 1 again: heuristics.html. This lesson needs them a lot.

    Complete: always yes, if b is finite and every cost ≥ ε > 0 (like UCS).
    
        
    Remember: tree search needs an admissible h. Graph search needs a consistent h.
    
          Consistent ⇒ admissible, so a consistent h is good for both.
    
        
    A common mistake: "tree search needs consistent, graph search needs admissible". No!
          It is the other way. Graph search skips a city that it already expanded. If it came the first time by an expensive road,
          the cheap road is lost. Only the stronger test (consistent) makes sure the first time is the cheapest time.
          Tree search never skips, so admissible is enough.
    
        
    Some books use a graph search that puts an explored city back in the queue when a cheaper path to it is found
          ("re-opening"). With re-opening, admissible is enough. Our code does not re-open.
    
        
    Time and space
    
        
    Worst case: exponential, like UCS: O(bd). A* keeps all nodes in memory,
          so memory is its biggest problem. A better h means fewer nodes:
    
        
    
        
    If h2(n) ≥ h1(n) for every n, and both are admissible, h2 is better: A* expands fewer (or the same) nodes.
          Example: in the 8-puzzle, Manhattan distance is better than misplaced tiles.
    
      
    

      
    
        
    
          
    Why does it work?
    
          
    Admissible: on the cheapest path, f = g + h is never more than the real cost C*.
            So a node on the cheapest path always comes out of the queue before a goal with a bigger cost.
    
          
    Consistent: along any path, f never goes down. On our cheapest path:
    
          
    S0+14=14→A10+8=18→C15+3=18→F17+1=18→G18+0=18
    
          
    So A* takes nodes in order of f, and the first time it takes a city, it came by the cheapest path.
            That is why graph search can skip the next copies safely.
    
          
    Why f never goes down: f(child) = g + c + h(child) ≥ g + h(node) = f(node), because consistent means h(node) ≤ c + h(child).
    
        
    
        
    
          
    What if h is too big?
    
          
    Guess "too big at A": h(A) = 15, but the real cost is 8. A* thinks the trip through A costs 10 + 15 = 25.
            The path through B and E costs 21 < 25, so A* returns it. 21 km, not 18.

    What went wrong?
    
          
      
            
    1. A* takes A first by the long road S → A (g = 4). A is now explored.
      2. 
            
    2. Later it finds A by the short road S → B → A (g = 2).
      3. 
            
    3. But A is explored, so graph search skips this cheap copy (the red row). The cheap way to A is lost.
      4. 
          
    
          
    Why did the cheap copy come too late? Look at f on the path S → B → A: 4 → 6 → 2.
            f goes down, because the guess drops by 5 on a road of 1 km.
            With a consistent h, f never goes down on a path, so the cheapest copy of a city always comes out of the queue first.
    
        
    
        
    
          
    And tree search?
    
          
    Tree search does not skip anything. It expands A again with g = 2, and finds S → B → A → G = 7 km. Optimal.
            That is why tree search needs only an admissible h.
    
          
          
    
          
    How to fix graph search
    
          
      
            
    • use a consistent heuristic (the best fix), or
      • 
            
    • use tree search (but it can expand the same city many times), or
      • 
            
    • "re-open": when a cheaper path to an explored city is found, put it back in the queue (our code does not do this).
