Breadth-First Search (BFS)

Intelligent Search Algorithms · Latakia University · Our first search algorithm

The idea

You lost your keys at home. You do not run to the far rooms first. You look near you first, then a bit further, then further again.

BFS searches the same way. It looks at all the places 1 step away, then all the places 2 steps away, then 3 steps away, and so on. Like a stone in water: the circles grow one by one.

BFS in one sentence: always expand the shallowest node first (the node with the smallest depth).

How does BFS remember the order?

With a queue, like the line at a bakery: the first person in the line is served first. This is called FIFO: First In, First Out.

  • New nodes go to the back of the queue.
  • BFS always takes the node at the front of the queue.

So old (shallow) nodes are always served before new (deep) nodes.

    1 · Check when adding graph search
    
          
    In the standard code, D goes into the queue two times: once from A and once from B.
            We skip the second D later, but it waits in the queue and uses memory.
    
          
    The fix: remember a state at the moment we add it to the queue, not when we expand it.
            Now the set has every state we generated (in the queue or expanded), so we call it reached.
    
          
    
          
    The lines with ★ are new. The answer is the same. Each state goes into the queue only once.
    
          
    
            
    exploredthe state was expanded (standard BFS)
    
            
    reachedthe state was generated: it is in the queue or it was expanded
    
          
    
          
    Why not "visited"? Many books and websites use this name, but for two different things:
            some mean "added to the queue", others mean "expanded". So we use reached, the name in the AIMA book.
    
          
    Where did explored go? We do not need it:
            
      
              
    • Every expanded state is already in reached.
      • 
              
    • No state goes into the queue twice, so there is nothing to skip.
      • 
              
    • In BFS the first path to a state is the shortest one, so we never change it.
      • 
            
    
            In UCS and A* a cheaper path can come later, so there we need it again.
    
          
    Java: BFSOptimized.java. Try it in step 2 with "Graph + check when adding".
    
        
    

        
    
          
    2 · Early goal test exercise
    
          
    Now we test the goal when we create a child, not when we take it out of the queue.
    
          
    Why is it still correct? BFS creates the nodes level by level.
            So the first goal we create is also on the smallest depth.
    
          
    What do we save? With the normal test, before the goal (depth d) comes to the front of the queue,
            we already created many nodes of depth d+1. With the early test we stop before that:
            about bd nodes instead of bd+1. That is one full level less.
    
          
    
          
    Be careful: do not forget the start node: test it before the loop.
            And this trick is good for BFS only. In UCS and A* the first goal we create can be an expensive one.
    
          
    Exercise: copy BFSOptimized.java to BFSEarlyGoal.java and add this change.

    Is BFS good?
    
        
    b = branching factor (the number of children of a node), d = depth of the nearest goal.
    
        
    
          
    QuestionAnswerWhy
    
          
    Complete?
    Does it always find a solution if one exists?    		
            YesIf b is finite. BFS checks all levels in order, so it must reach level d.
    
          
    Optimal?
    Is the solution the cheapest?    		
            Yes, but only if all steps have the same costBFS finds the path with the fewest steps. Fewest steps = lowest cost only when every step costs the same.
    
          
    TimeO(bd)The number of nodes it creates. With our normal goal test it can be O(bd+1).
    
          
    Space (memory)O(bd)The queue keeps a whole level of nodes. This is the real problem of BFS.
    
        
    

        
    When is BFS not optimal?
    
        
        
    BFS takes S → G: 1 step, but cost 10.
          The path S → A → B → G has 3 steps, but cost only 3.
    
        
    Remember the maze with mud (cost 3)? There, the path with the fewest steps is not always the cheapest one.
          So BFS is not optimal there. For different costs we need Uniform Cost Search (UCS), our next algorithm.

    Mistakes to avoid
    
          
      
            
    • Create the queue and the set inside search(), not as fields.
              If they are fields, a second search starts with old nodes inside.
      • 
            
    • Call resetCounters() at the start, or the numbers of two searches are added together.
      • 
            
    • Use a HashSet for explored, not an ArrayList.
      • 
            
    • Do not use frontier.contains(): it checks every node in the queue.
      • 
            
    • Write equals() and hashCode() in your State class.
