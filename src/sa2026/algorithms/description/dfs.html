Depth-First Search (DFS)

Intelligent Search Algorithms · Latakia University · Go deep first

The idea

You are inside a maze. You do not try every corridor a little bit. You choose one corridor and walk to its end.

At a dead end, you go back to the last crossing and try the next corridor there. This "go back and try another way" is called backtracking.

DFS in one sentence: always expand the deepest node first (the newest node we found).

BFS was careful: near places first. DFS is brave: it goes deep first, and comes back only when it must.

How does DFS remember the order?

With a stack, like a pile of plates: you put a plate on the top, and you take a plate from the top. This is called LIFO: Last In, First Out.

  • New nodes go on the top of the stack (push).
  • DFS always takes the node on the top (pop).

So the newest (deepest) node is always taken first.

    The problem: cycles
    
          
    In step 3 we saw it: DFS tree search goes S → B → S → B ... forever.
    
          
    What is a cycle? One path that comes back to a state that is already on the same path.
            
      
              
    • A cycle: S → A → S. The second S is already on this path (it is the start of it).
      • 
              
    • Not a cycle: S → A → D and S → B → D. D is on two different paths, not twice on one path.
      • 
            
    
          
    Tree search does not remember anything, so it visits states again all the time. Visiting a state again
            in another branch only costs time (see "Be careful" in this step). But a cycle is worse:
            DFS always goes deeper on the same path, so it goes S → A → S → A ... and never comes back.
            In BFS, tree search was only slow. In DFS it can be stuck forever.
    
          
    So DFS must be able to say: "do not go there, this state is already on my path".
            There are two ways to do it. Think of a man walking in a maze:
    
          
    
            
    Chalk marks
    = explored set (graph search)    		A thread

    How?Draw a mark in every room you leave. Never go into a marked room again.
              Tie a thread at the door and unroll it as you walk. When you go back, roll it up again.
                Do not go into a room where your thread already is.
    
            
    What does it remember?Every room you have ever expanded.Only the rooms on your way now, from the door to you.
    
            
    How does it grow?Always bigger. The marks never go away.Up and down. It gets shorter when you go back.

    Why does the thread find cycles? A cycle means "I came back to a room I am still in the middle of".
            That room is on my way now, so my thread is in it. Rooms I left long ago (and rolled up) are not cycles.

            (in recursive DFS, it is the call stack). In the classic DFS from graph theory, the nodes on the current path are called
            gray, and an edge to a gray node is a back edge, which means a cycle. BFS cannot do this: it jumps between branches, so it has no single path.

    1 · Depth-limited search (DLS)
    
          
    Some search trees are very deep or even infinite (for example, counting numbers: 1, 2, 3, ...).
            DFS can go down forever and never come back.
    
          
    The fix: give DFS a limit L. A node at depth L is not expanded.
            DLS also uses the path check from step 4.
    
          
    
          
    
            
    L < dThe goal is too deep. DLS finds nothing. Not complete.
    
            
    L = dThe best case. DLS finds a shortest path (if all steps cost the same).
    
            
    L > dDLS finds a goal, but maybe a long path. Not optimal.
    
          
    
          
    Two kinds of "no": cutoff = "maybe there is a goal deeper than L",
            failure = "no goal at all". DLS returns cutoff if at least one node stopped at the limit.
    
          
    Try it in step 2 with "Depth-limited". Change the limit with − and +.
    
        
    

        
    
          
    2 · Iterative deepening (IDS)
    
          
    The problem of DLS: we must guess L, but we do not know the depth of the goal.
            So IDS tries every limit: L = 0, then 1, then 2, ... until it finds the goal.
    
          
    
          
    Why does IDS find the shortest path?
    
          
    With limit L, DLS looks at every node with depth ≤ L.
    
          
      
            
    • Limits 0, 1, ..., d−1 are too small. They cannot see the goal.
      • 
            
    • Limit d is the first limit that can see the goal. So the goal we find has depth d.
      • 
          
    
          
    That is a shortest path: the same answer as BFS. Try it in step 2: IDS and BFS find the same number of steps.
    
          
    Is the repeated work a big waste?
    
          
    IDS makes the top levels again and again. But most of the nodes are on the last level,
            and the last level is made only once.

    The gain: IDS gives the answer of BFS with the memory of DFS.
            We pay a little more time to save a lot of memory. And memory is the real problem of BFS: it runs out first.
    
          
    What do we gain from iterating?
            
      
              
    • DFS alone: small memory, but maybe a long path, or it never ends.
      • 
              
    • DLS alone: good only if we guess L = d. We do not know d.
      • 
              
    • Iterating: we try the small limits first, so the first goal we meet is the nearest one. Like the levels of BFS!
      • 
            
    
            BFS keeps a whole level in memory. IDS does not keep it: it makes it again in the next iteration.
            Keeping costs memory. Making again costs only a little time.
    
          
    When is BFS better? IDS does not remember states. When there are many paths to the same state (like in a maze),
            IDS repeats a lot of work (look at "The numbers" below). If there is enough memory, BFS is faster there.

    Is DFS good?
    
        
    b = branching factor, d = depth of the nearest goal, m = the maximum depth of the tree (it can be infinite).
    
        
    
          
    QuestionAnswerWhy
    
          
    Complete?
    Does it always find a solution if one exists?    		
            NoTree search can go around a cycle forever, or go down an infinite path.
              Yes with graph search (or the path check) when the number of states is finite.
    
          
    Optimal?
    Is the solution the cheapest?    		
            NoDFS returns the first goal it finds, not the nearest one.
    
          
    TimeO(bm)In the worst case it visits the whole tree. m can be much bigger than d.
    
          
    Space (memory)O(b·m)Tree search keeps only one path and the brothers of each node on it.
            This is the big win of DFS. (Graph search loses it: the explored set can hold all states.)
    
        
    

        
    When is DFS not optimal?
    
        
        
    
        
    Good for DFS: deep trees with many goals (puzzles like Sudoku or N-Queens), and small memory.
    
          Bad for DFS: a goal near the start in a very deep (or infinite) tree, or when we need the shortest path.

    Mistakes to avoid
    
          
      
            
    • Use push() and pop() together. add() puts the node at the bottom of an ArrayDeque.
      • 
            
    • Do not run DFS tree search on a graph with cycles: it may never stop. Use graph search or the path check.
      • 
            
    • Create the stack and the set inside search(), not as fields.
      • 
            
    • Call resetCounters() at the start. In IDS, add the counters of every iteration.
      • 
            
    • Write equals() and hashCode() in your State class (for the set and for the path check).
